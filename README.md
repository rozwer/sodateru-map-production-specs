## 固定する前提と、今回レビューする案

固定する前提は、独立したクリーンなリポジトリ、分割したローカル仕様書、仕様書内の画像、4人の並列作業、Aさんによる全UIの統括です。Aさんは一つのCodexで逐次実装するのではなく、共通UIを整えた後、複数Codexへ画面実装を並列に渡します。

今回レビューするのは、フォルダ構成、共通化の範囲、B〜Dさんの初期分担、機能Issueの粒度です。担当とフォルダを固定対応させません。API・DBの全実装を一人へ集めません。

## 範囲

4タブの主要機能をもとに分割を検討しています。既存機能の存在を本番への採用決定とは扱いません。iOSなどの理想機能は今回の着手列から外します。Web健康取込・相棒・体験移植など、今回の採否が決まっていない機能は担当候補だけを示します。

詳細な製品要件、全画面の採用画像、API・スキーマ、登録可能なIssueは、この構成のレビュー後に作成します。この初稿を、そのまま実装開始用の指示にはしません。

調査基準はリハーサルの `12e776b6d11c8305db4bbee22f28be418b4fadfd` です。構成判断に用いた事実は、地図が複数画面で共有されていること、体験記録が地図・共有・自己理解で使われていること、経路とAI実行に再利用箇所があることです。
