# 4. 仕様書・Issueの形式

[入口へ戻る](../../README.md)

## 文書ごとの役割

| 文書 | 書くこと |
|---|---|
| 要件書 | 利用者が何のために何をできる必要があるか、今回の対象と対象外 |
| UI仕様 | 画面・状態・画像・入力・操作・遷移・表示結果 |
| 処理仕様 | 入出力、保存、再取得、外部呼出し、失敗・再送・取消 |
| 契約 | APIの型、初期スキーマ、共用する入出力例 |
| 受入 | 具体的な操作・入力と期待結果。UI、処理側、実接続の確認結果 |
| Issue | 誰がどの仕事をどこまで完成させるか、必要な参照先と依存 |

実装者は担当する仕様と契約を読めば着手できる形にします。旧リポの経緯や、複数文書の「こちらを優先」という追記を読み解かせません。

## 画面と画像

全画面と全分岐を一覧化し、見た目が異なる状態を撮影します。同じ見た目になる入力の組合せは、画像を増やす代わりに条件表へ記載します。

画像は対象仕様の `images/` に置き、状態ID、画面幅、再現条件、撮影した版を付けます。「現状の記録」「採用する完成仕様」「修正が必要な参考」を区別します。現状の不具合を完成仕様にしません。

読み込み中、空、入力中、保存中、成功、失敗、再試行、権限なしなど、その画面に該当する状態を対象にします。スマホ幅と広い画面の差も定義します。

### 操作表

| 操作ID | 要素・入力 | 有効条件 | 遷移・呼出しと渡す値 | 成功時 | 失敗・再試行時 |
|---|---|---|---|---|---|
| 機能ごとの安定ID | ラベルまたは文言キー | 未入力・処理中などを含む | 遷移先、API名、対象ID・入力 | 表示、保存、再取得 | 入力保持、エラー、再送、戻る |

ボタンだけでなく、リンク、フォーム、タブ、地図選択、戻る、閉じるも対象です。「保存APIを呼ぶ」で終わらず、保存中の再操作、失敗時の入力保持、開き直した結果まで書きます。

## 受入の書き方

「正常に動く」「UIがある」では通過条件になりません。初期データ、入力、操作、期待する表示・保存結果を一組にします。

例えば体験記録なら、次のように分けます。実際のAPI名・項目・成長規則は、その機能の仕様作成時に確定します。

| 対象 | 受入例 |
|---|---|
| UI | 指定した場所と本文を入力して保存すると、契約どおりの値を送信し、保存結果が表示される |
| 処理側 | 同じ入力を実APIへ送ると保存され、再取得・再起動後も同じ本文と場所を返す |
| 失敗 | 保存失敗を返すと画面に入力が残り、再試行できる。応答喪失後の同じ操作の再送で二重登録しない |
| 訂正 | 保存済みの本文・用途を訂正すると、同じ体験の最新内容を取得でき、成長結果も定義した規則に従って更新される |
| 実接続 | 実画面で追加・訂正し、履歴と地図から同じ保存結果を確認できる |

## Issue本文の最小形式

```markdown
# [担当] 完成させる機能・操作

## 完成結果
利用者または呼出し側が、何を入力し、何を得られるか。

## 実装範囲
含める処理・対象外。API・保存・固有の失敗処理を含む範囲を明記。

## 参照
仕様の節、画面・操作ID、API契約、スキーマ、入出力例、受入ID。

## 通過条件
具体的な正常・失敗・再取得の条件と、必要な証拠。

## 依存と編集範囲
使う共通処理、依存が未提供でも進められる作業、最終確認に必要な接続。
編集する機能・共有ファイルと、変更が必要な場合の相手。
```

UI Issueと処理側Issueは、同じ機能仕様・受入IDを参照します。画像や仕様本文をIssueへ複製せず、対応するローカル文書への参照を載せます。

API契約・スキーマ・入力例が未確定のまま、実装者に補完させるIssueは登録しません。今回作成したのは形式の案であり、上の例は実装開始可能なIssueではありません。
