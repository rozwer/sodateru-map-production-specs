# 2. 担当と作業単位

[入口へ戻る](../../README.md) · [次：並列作業と接続](03-execution.md)

## Aさんは全UIの責任者

AさんがUI共通基盤を整え、その後、複数Codexへ画面群を並列に渡して全UIを完成させます。Mapbox描画、チャット部品、画面状態、API呼出し、モック、全分岐の確認もAさんの範囲です。

文言・翻訳は `messages.ts` の1ファイルに集約します。対象はラベル、案内、空・エラー表示、入力補助、アクセシビリティ名などの固定UI文言です。利用者の投稿やAIの回答はデータとして表示し、翻訳辞書へ入れません。

Aさん配下のCodexは、共通部品・テンプレートと文言キーを使って画面を実装します。文言・トークン・テンプレートの追加変更はAさんがまとめ、複数Codexによる同じ共通ファイルの同時編集を避けます。

## 共通実装の境界

| 一度実装するもの | 初期の管理担当 | 利用機能が持つもの |
|---|---|---|
| 文言・翻訳、トークン、部品、テンプレート、共通ナビ | A | 画面固有の構成・操作 |
| Mapbox生成・破棄、カメラ、2D/3D、地点・経路・建物・レイヤー、選択イベント | A | 表示データ、機能固有の条件 |
| チャット表示・入力・処理中・取消・再試行 | A | 相談目的、対象、結果を使う操作 |
| AI接続、会話・ジョブの保存、実行・取消・結果形式の検証 | D | プロンプト、入力の組立、固有結果の適用 |
| 場所検索・経路取得、共通の地理データ形式 | C | 固有の条件、候補選択、採用結果 |
| 体験・媒体・訪問・訂正の保存 | B | 履歴・共有・分析からの利用 |
| 起動・DB接続・共通エラーなどの薄い処理 | Bが最初の機能で整備 | 各機能のAPI・SQL・保存処理・テスト |

**Bさんは全API・DBの担当ではなく、Dさんは全AI機能の担当ではありません。** 例えばCさんは、共通AI実行を使って地図設定のプロンプト・結果検証を実装し、そのAPI・保存も担当します。

同じMapboxでも描画はAさん、サーバーからの経路取得はCさんです。チャットの画面はAさん、共通AI実行はDさんです。各境界は `contracts/map.ts` と `contracts/chat.ts`、機能APIで定義します。

## 処理側の初期分担

以下のUIはすべてAさんが担当します。表は処理側の初期配分であり、未着手の機能はB〜Dさんの間で移せます。

| 機能のまとまり | 初期担当 | その担当が仕上げる処理側の範囲 |
|---|---|---|
| 利用開始・設定・復帰 | B | 本人領域、設定、状態保存、データ管理、起動・配置 |
| 記録から地図が育つ | B | 訪問・体験・写真動画、履歴、訂正・削除、成長の算出 |
| 場所を探して案内する | C | 地点・建物、検索、経路取得・保存、案内状態 |
| 探索候補から行動へ進む | C | 候補、発見・関心、採用、経路への受渡し |
| 振り返る | D | 質問・回答・日記。体験の保存・訂正は共通の記録処理を利用 |
| 傾向と根拠を確かめる | D | 期間別分析、根拠、訂正、本人ルール |
| 次の過ごし方を選ぶ | D | 現在の希望、提案、選択と評価。場所・経路の取得は共通処理を利用 |
| テーマ・メモ・比較を残す | D | 作成・編集・削除、元記録との対応、保存済み内容の再取得 |
| 友人の体験を共有・比較する | B | 共有範囲、友人の地図・軌跡、比較、公開ルート |
| 地域の知を投稿・訂正する | B | 地域情報、原文、出典、公開・取消。体験・共有の保存を再利用 |
| 拡張機能を導入・管理する | B | ストア、導入・停止・削除、設定、要望 |
| 地図の見た目を調整する | C | 設定の定義・検証、AI依頼の固有処理。描画と操作はAさん |
| 防災プラグインを使う | C | 外部情報、地形・雨量等の計算、結果保存、根拠の再取得 |
| バイクプラグインを使う | C | 固有地点、通行条件、固有経路、設定と結果保存 |
| 聖地プラグインを使う | D | 作品・地点・説明、巡回計画、設定と結果保存。経路取得は共通処理を利用 |

処理側の担当は、API・業務処理・必要なSQL・再読込・固有の失敗検証まで持ちます。「APIだけ」「DBだけ」「最後の接続だけ」に切り分けません。

## Issueの大きさ

表の「記録から地図が育つ」は、保存・訂正・成長まで一つの処理側Issueにまとめる候補です。「傾向と根拠」「次の過ごし方」は、別の操作・結果として別Issueにできます。部品・関数・テーブルごとのIssueにはしません。

UIは「共通UI」と「画面群」の作業単位でAさんが管理します。画面群の並列化はAさん配下で行い、ボタンや状態一つずつを独立Issueにしません。UI Issueと処理側Issueは、同じ仕様の操作ID・受入条件を参照します。

## 今回の採否を別に決める機能

| 機能 | 採用する場合の処理側担当候補 |
|---|---|
| Webからの健康ファイル取込・集計 | B。AI利用は共通AI実行を使う |
| 相棒の取込・生成・保存 | D。表示・管理UIはA |
| 体験レシピ・他地域への移植 | C。元体験・AI・経路を再利用 |
| 外部資料の取込・更新・修復 | C。固有のAI処理は共通AI実行を使う |

これらは空き時間を埋めるための仕事にしません。採用を決めたものだけ本番の作業列へ入れます。iOS等の理想機能は今回の分担対象外です。
